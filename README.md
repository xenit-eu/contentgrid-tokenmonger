# ContentGrid Tokenmonger

Tokenmonger manages JWT authentication tokens for ContentGrid extensions.

It creates the following types of tokens:

* User Extension Access Token: Authenticates a ContentGrid user to a specific ContentGrid extension
* Extension Application Access Token: Authenticates a ContentGrid extension to a ContentGrid application
* Extension Delegated Application Access Token: Authenticates a ContentGrid extension acting on behalf of a ContentGrid user to a ContentGrid application

## Usage

### Obtaining tokens

Tokenmonger follows the OAuth 2.0 specification for exchanging authentication tokens.

A user is responsible for obtaining a user token from an OAuth/OpenID Connect authentication provider.
An extension is responsible for obtaining an Extension Identity Token from an OAuth/OpenID Connect authentication provider.
Tokenmonger does not authenticate users/extensions or issue tokens that directly identify them.

There are 2 different flows involved:
1. To have the user authenticate to the extension, and then have the extension authenticate to a ContentGrid application on behalf of the user
   1. Authenticate a user to a ContentGrid extension
      This initial exchange happens in the same context as in which the user is authenticated (user token is not sent to an additional origin)
      Make a POST request to `<app domain>/.contentgrid/authentication/external/token`, using `grant_type=https://contentgrid.cloud/oauth2/grant/extension-token` 
      and the `resource` parameter set to the external resource(s) you want to request. Send the user token in the `Authorization` header.
      You will receive back a standard OAuth token response with an `access_token` (no refresh tokens are issued)
      This newly-issued access token is now sent to the extension as a bearer token in the `Authorization` header.
   2. Authenticate a ContentGrid extension to a ContentGrid application on behalf of a user
      A ContentGrid extension can obtain a delegated authentication token to make requests to a ContentGrid application on behalf of the user that is using the extension.
      This makes use of OAuth 2.0 Token Exchange, with `subject_token` set to the users' external authentication token from step 1 and the `actor_token` set to the ContentGrid extension identity token (from an external IDP).
      The token endpoint is at `<tokenmonger domain>/authentication/delegated/token`
      You will receive back a standard OAuth token response with an `access_token` (no refresh tokens are issued)
2. To have the extension authenticate directly to a ContentGrid application on its own behalf
   1. Obtain an Extension Identity Token by authenticating to the OAuth/OIDC authentication provider using client credentials
   2. Exchange the Extension Identity Token for an Extension Application Access Token using an OAuth 2.0 Token Exchange, with `subject_token` set to the extension identity token from step 1.
      The token endpoint is at `<tokenmonger domain>/authentication/system/token`
      You will receive back a standard OAuth token response with an `access_token` (no refresh tokens are issued)

## Configuration

### JWT verification

Tokenmonger consumes two types of externally-provided JWTs, for which verification settings must be configured.
 * User Application Access Token: Authenticates a user to a ContentGrid application
   A token derived from this is generated by the ContentGrid gateway when proxying the application domain to Tokenmonger
 * Extension Identity Token: Authenticates an extension to Tokenmonger.

| Property                                                         | Type        | Description                                                                                                                   |
|------------------------------------------------------------------|-------------|-------------------------------------------------------------------------------------------------------------------------------|
| `contentgrid.tokenmonger.user-application-access.issuer`         | URI         | Issuer for the User Application Access Token (typically not set, as different issuers are trusted for different applications) |
| `contentgrid.tokenmonger.user-application-access.jwk-set-uri`    | URI         | JWK set for verifying the User Application Access Token                                                                       |
| `contentgrid.tokenmonger.user-application-access.audience`       | string list | Expected value(s) of the `aud` claim in the  User Application Access Token                                                    |
| `contentgrid.tokenmonger.user-application-access.jws-algorithms` | string list | Signing algorithms trusted for the User Application Access Token                                                              |
| `contentgrid.tokenmonger.extension-identity.issuer`              | URI         | Issuer for the Extension Identity Token                                                                                       |
| `contentgrid.tokenmonger.extension-identity.jwk-set-uri`         | URI         | JWK set for verifying the Extension Identity Token                                                                            |
| `contentgrid.tokenmonger.extension-identity.audience`            | string list | Expected value(s) of the `aud` claim in the  Extension Identity Token                                                         |
| `contentgrid.tokenmonger.extension-identity.jws-algorithms`      | string list | Signing algorithms trusted for the Extension Identity Token                                                                   |

To be able to verify a JWT, at least either `issuer` or `jwk-set-uri` must be configured.

- When `issuer` is present, the `iss` claim of JWTs is validated to match it.
- When `jwk-set-uri` is present, the JWKs retrieved from that URL will be used to validate JWTs.
- When `jwk-set-uri` is not present, [RFC8414] Authorization Server Metadata will be resolved for the `issuer` to determine the `jwks_url`.

### JWT issuers

For every kind of token, Tokenmonger has a different JWT issuer and separate signing keys.

The issuer URI and the locations on the filesystem where signing keys can be found are configured separately for every token type.
Signing keys can be provided in PEM or JWK format, with one key per file.

Both active and retired signing keys can be provided. Only active keys are used for signing tokens.
Retired keys are served on the JWK Set endpoint so already issued tokens can still be verified.
Signing keys are regularly (but not immediately) reloaded from filesystem.

| Property                                                                              | Type             | Description                                                                                         |
|:--------------------------------------------------------------------------------------|------------------|-----------------------------------------------------------------------------------------------------|
| `contentgrid.tokenmonger.user-extension-access.issuer`                                | URI              | Issuer for the User Extension Access Token                                                          |
| `contentgrid.tokenmonger.user-extension-access.active-signing-keys`                   | location pattern | File pattern to load active signing keys from for the User Extension Access Token                   |
| `contentgrid.tokenmonger.user-extension-access.retired-signing-keys`                  | location pattern | File pattern to load retired signing keys from for the User Extension Access Token                  |
| `contentgrid.tokenmonger.user-extension-access.jws-algorithms`                        | string list      | Signing algorithms used for the User Extension Access Token                                         |
| `contentgrid.tokenmonger.extension-application-access.issuer`                         | URI              | Issuer for the Extension Application Access Token                                                   |
| `contentgrid.tokenmonger.extension-application-access.active-signing-keys`            | location pattern | File pattern to load active signing keys from for the Extension Application Access Token            |
| `contentgrid.tokenmonger.extension-application-access.retired-signing-keys`           | location pattern | File pattern to load retired signing keys from for the Extension Application Access Token           |
| `contentgrid.tokenmonger.extension-application-access.jws-algorithms`                 | string list      | Signing algorithms used for the Extension Application Access Token                                  |
| `contentgrid.tokenmonger.extension-delegated-application-access.issuer`               | URI              | Issuer for the Extension-Delegated Application Access Token                                         |
| `contentgrid.tokenmonger.extension-delegated-application-access.active-signing-keys`  | location pattern | File pattern to load active signing keys from for the Extension-Delegated Application Access Token  |
| `contentgrid.tokenmonger.extension-delegated-application-access.retired-signing-keys` | location pattern | File pattern to load retired signing keys from for the Extension-Delegated Application Access Token |
| `contentgrid.tokenmonger.extension-delegated-application-access.jws-algorithms`       | string list      | Signing algorithms used for the Extension-Delegated Application Access Token                        |

For every JWT issuer least `issuer` and `active-signing-keys` properties must be configured.
URLs for the token-endpoint and JWK Set are automatically exposed underneath on the configured `issuer` URL; [RFC8418] Authorization Server metadata is also available

### Extension registration

For some token requests, Tokenmonger needs to resolve a `resource` parameter to an extension.

The configuration needed for this can be configured in the extension registration configuration.

| Property                                                             | Type           | Description                                                                                                 |
|----------------------------------------------------------------------|----------------|-------------------------------------------------------------------------------------------------------------|
| `contentgrid.tokenmonger.extensions.registration.*.extension-id`     | string         | Unique identifier of the extension. This value is used as `sub` in Extension Identity Tokens.               |
| `contentgrid.tokenmonger.extensions.registration.*.resource-uris`    | list of URI    | List of resource URIs used by the extension.                                                                |

### Application discovery

For some token requests, Tokenmonger needs to resolve a `resource` parameter to an application.

The discovery of which resources belong to which applications is done using [ContentGrid configuration discovery](https://github.com/xenit-eu/contentgrid-configuration-discovery/),
which can read configuration from Kubernetes or from local properties.

[RFC8414]: https://www.rfc-editor.org/rfc/rfc8414.html
